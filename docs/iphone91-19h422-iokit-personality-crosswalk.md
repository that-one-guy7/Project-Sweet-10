# iPhone9,1 19H422 IOKit personality crosswalk

## Purpose and evidence boundary

This report records a read-only comparison between the embedded IOKit personality metadata returned by `ipsw kernel kexts --json` for the iPhone 7 iOS 15.8.8 (19H422) KernelCache and the allowlist-filtered target DeviceTree summary already committed in this repository.

The physical iPhone remains on iOS 12.1.4. The 19H422 KernelCache and DeviceTree are separate host-side reference artifacts. They are not installed on the phone. This is not the iPhone X 20H392 donor kernel or userland.

The findings below establish static metadata overlap at the name/property level. They do not establish that a KEXT is loaded, that IOKit actually matches or attaches it at runtime, that a peripheral works, or that any part of the 19H422 kernel can be transplanted into the 20H392 system.

## Inputs

### Target KernelCache

The user's 19H422 KernelCache inventory reports:

- Product: iPhone9,1 / D10AP / A10-T8010.
- Darwin 21.6.0; XNU `8020.241.44~1`.
- Kernel target: `RELEASE_ARM64_T8010`.
- KernelCache SHA-256: `7b40304d4da951afb6c842477fdfe7ad141a304d32c25ade73d35eb14b238aee`.
- KEXT list: 230 entries.

The personality output was generated by ipsw 3.1.749 using its JSON KEXT listing. Nine requested candidate bundle IDs were found; eight returned an `io_kit_personalities` field, while `AppleMultitouchSPI` did not expose that field in the supplied JSON output.

### Interpretation

- The display personality matches the target display node by name and advertises `AppleARMIODevice` as its provider class.
- The Synopsys MIPI-DSI controller personality now has an exact compatible-string overlap with the target parent node `/arm-io/mipi-dsim`; its provider class is also `AppleARMIODevice`.
- The Samsung SPI personality matches the target SPI controller node by name and also uses `AppleARMIODevice`.
- The SPI HID transport personality matches the target K1 touch node's compatible string and expects an `AppleARMSPIDevice` provider. This is the clearest target-specific touch-transport personality overlap in the supplied data.
- The Pinot LCD personality matches the target panel compatible string and expects an `AppleARMMIPIDSIDevice` provider.
- The LM backlight personality explicitly includes the target's `backlight,lm3539` compatible string and expects an `AppleARMIICDevice` provider.

The provider-class names are compatible with the kinds of parent/device relationships represented in the DeviceTree paths, but this static summary alone does not establish the live IOKit service graph, probe order, successful attachment, or operational hardware.

## Related personalities and unresolved links

### MIPI-DSI controller

The `AppleSynopsysMIPIDSI` bundle reports the personality:

- Name: `AppleSynopsysMIPIDSIController`.
- Provider class: `AppleARMIODevice`.
- `IONameMatch`: `mipi-dsim-1,synopsys`.

The follow-up raw-tree inspection confirms that `/arm-io/mipi-dsim` has `compatible = mipi-dsim-1,synopsys`, exactly matching the `AppleSynopsysMIPIDSIController` personality's `IONameMatch`. This is a sixth direct static name-level overlap. It remains evidence of metadata compatibility only; it does not prove that the controller KEXT loads or attaches at runtime.

### Multitouch HID service and SPI plugin

The `AppleMultitouchDriver` bundle reports several personalities whose provider class is `IOHIDInterface`. The relevant usage-pair entries include:

- Usage page `0x0D`, usage `0x04`.
- Usage page `0x0D`, usage `0x20`.
- An additional vendor-defined pair: usage page `0xFF60`, usage `0x1002`.

For the `0x0D/0x04` and `0x0D/0x20` personalities, `DefaultMultitouchProperties` includes `HIDServiceSupport`, and `IOCFPlugInTypes` references:

`AppleMultitouchSPI.kext/PlugIns/MultitouchHID.plugin`

This creates a documented static relationship between the generic multitouch HID service personality and the SPI multitouch plugin path. Although the `AppleMultitouchSPI` KernelCache JSON record does **not** include an `io_kit_personalities` field, the user subsequently extracted the nested plugin's Info.plist from the matching 19H422 filesystem DMG. The plist identifies `com.apple.iokit.plugin.MultitouchHID`, version `5100.27`, minimum OS `15.8`, and an `IOHIDPlugInFactory` mapping. Its plug-in type UUID matches the type key referenced by the `AppleMultitouchDriver` personalities. This confirms the nested plugin metadata and its static factory mapping; the executable binary, cryptographic signature validation, runtime activation, and event path remain unverified.

The plugin's `CFPlugInTypes` type UUID is `0516B563-B15B-11DA-96EB-0014519758EF`. It maps to factory UUID `0CB0FBB9-15EA-11DB-A93C-001451D47183`, whose declared function is `IOHIDPlugInFactory`. The user's extraction output listed both `Info.plist` and `_CodeSignature/CodeResources`; it did not list the plugin executable.

The general `AppleHIDTransport` bundle reports a dummy transport personality matching `hid-transport,dummy` and a second personality for an `AppleHIDTransportInterface` with `InterfaceType = HID`. The exact target K1 string is matched by the separate `AppleHIDTransportSPI` personality, not by either of these general `AppleHIDTransport` personalities.

### Display/backlight relationship hint

The `AppleMobileDispH9P` personality contains a `BacklightMatching` dictionary with an `IOPropertyMatch` requiring `backlight-control = true`. The follow-up inspector output does not report this property on `/arm-io/disp0`, so the target DeviceTree does not establish that this additional backlight-matching condition is met on that node. This does **not** erase the direct `disp0,t8010` personality overlap; it leaves the separate display-to-backlight association unconfirmed. Independently, `/arm-io/i2c0/lm3539` still has the exact `backlight,lm3539` match for the `AppleLMBacklight` personality.

The `AppleLMBacklight` bundle also exposes a separate `AppleSPMIBacklight` personality for `pmu,d2483` and `pmu,d2652`. That SPMI personality is distinct from the I2C `backlight,lm3539` match relevant to this target.

### Version formatting note

The text KEXT listing printed `AppleMobileDispH9P (140.0.0)`, while the JSON result printed its version as `140.0`. The bundle ID and personality content are unambiguous; the version-string discrepancy is retained rather than silently normalized.

## What this advances

The M5 static research is now materially stronger: six target hardware nodes have exact name-level overlaps with personalities from the target-native 19H422 KernelCache, including the display subsystem, Synopsys MIPI-DSI controller, Pinot panel, Samsung SPI controller, K1 touch transport, and LM3539 backlight. The multitouch metadata also records the HID-interface/plugin relationship that deserves further static study. The separate display-to-backlight `backlight-control` property condition remains unconfirmed.

This is still evidence from the iOS 15.8.8 target reference. It does not solve the separate XNU 8796 T8010 machine-profile gap, the static DeviceTree's zero clock/memory/panic fields, the custom loader handoff, or 20H392 userland compatibility.
